Self-XSS in Stirling-PDF's merge feature

Unsanitised PDF file names were rendered straight into the result page, so HTML and JavaScript in a file name got executed. Here's the bug, its impact, and the one-line fix.

While reviewing Stirling-PDF, I identified a vulnerability in the "Merge PDF" functionality that allowed users to execute arbitrary JavaScript in their own context. The issue stemmed from improper handling of untrusted input, specifically file names, when building the resulting HTML page. It was later assigned CVE-2024-52286.

Let's break down the problem, its impact, and how to address it.

The vulnerability

The merge functionality doesn't sanitise the file names of the PDFs being merged. When they're shown on the page they're used as-is, so any HTML tags and JavaScript in a name get executed.

Technical details

The problem originated in src/main/resources/static/js/merge.js, starting at line 24:

merge.js
23// render the selected file name
24document.getElementById("filename").innerHTML = userInputFileName;

Here userInputFileName is inserted directly into innerHTML, with no sanitisation or validation. An attacker can upload files whose names contain HTML or JavaScript, which then executes in the user's browser.

Proof of concept

  1. Create a file named <img src=x onerror=alert(1)>.pdf.
  2. Open the Merge PDF page and upload the file.
  3. The JavaScript runs and shows an alert box with the number "1".

The issue was also exploitable on the hosted site at stirlingpdf.io/merge-pdfs:

The impact

This is a self-injection attack: it relies on users uploading the malicious file themselves, and it affects only them. A user could still be socially engineered into doing so as part of a phishing attack, and it breaks the security restrictions the application expects to enforce.

Note
Self-XSS is usually rated low severity, but it's often a useful link in a longer chain, especially where file names come from a shared source.

Mitigation and remediation

  1. Sanitise user input

    Treat all user input as untrusted and encode special characters. For display, use textContent instead of innerHTML.

  2. Avoid assigning untrusted input to innerHTML

    It will execute any scripts embedded in the input.

  3. Use a sanitisation library

    Where you genuinely need HTML, use something like DOMPurify.

  4. Educate users

    Warn about suspicious file names where applicable.

The fix
One property change closes it: 
document.getElementById("filename").textContent = userInputFileName;

Closing thoughts

I reported the issue to the maintainer on 10 September 2024 and raised a pull request with a fix, which was accepted and merged in November 2024.
